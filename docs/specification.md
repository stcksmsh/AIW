# AIW workspace specification, version 1

This document separates the **AIW workspace contract** from the **Rust v0.1
reference implementation**. Another client can read and write the same files
without Rust or a provider SDK. “MUST” defines current interoperability behavior;
implementation notes are not promises about future clients.

## Authority and layout

A workspace root contains `.ai/state.json` with `schema_version: 1`. That file is
canonical. `.ai/policy.md` and `.ai/decisions/` contain durable human/agent policy
and settled decisions. Public documentation remains ordinary repository content.
`.ai/derived/` is reproducible data; `.ai/runtime/` is disposable. Clients MUST NOT
interpret derived data or old narrative as authority over source or canonical state.

The [JSON Schema](../schemas/workspace-v1.schema.json) describes the serialized
shape. Unknown fields in canonical typed objects MUST be rejected rather than
silently discarded. Optional nullable fields may be omitted. IDs are map keys:
1–64 ASCII alphanumeric characters, `_` or `-`. Clients MUST validate semantic
references and transitions in addition to JSON Schema. Text is UTF-8; the reference
client additionally bounds fields (4,096 bytes), lists (normally 64 items), commands
(32 per task) and serialized state (16 MiB). No timestamp has ordering authority.

The schema is generated by `aiw schema` and committed as an interchange artifact.
The Rust types are its current generator, not a requirement for other clients.
A test compares the generated schema with the published file.

## Entities

- `project`: name, description, invariant strings.
- `plans`: ID → title and coherent objective. Plan progress is derived from tasks;
  there is no separately mutable plan status.
- `tasks`: ID → title, plan ID, status, dependencies, relative scope paths,
  acceptance criteria, constraints, verification argv, worker, blocker, result,
  latest evidence. At least one acceptance criterion is required. Scope is a
  declared boundary, not an OS sandbox. Paths forbid absolute paths, `..`, `.`,
  backslashes, colon and control characters for portable interchange.
- `active_plan` / `active_task`: explicit intent. An active task MUST be nonterminal
  and belong to the active plan. Multiple in-progress tasks may exist.
- `checkpoint`: latest task ID (nullable), next action, and a short factual note.
  Git retains history. A checkpoint MUST NOT be a copy of a diff or log.

Claims record an opaque worker string. Provider/model identity has no semantic
role. Task-local findings belong in a short result or checkpoint; settled facts
that constrain future work should become an invariant or decision.

## State machine and DAG

| From | Allowed next states |
| --- | --- |
| pending | in_progress, blocked, cancelled |
| in_progress | blocked, done, cancelled |
| blocked | pending, in_progress, cancelled |
| done | pending |
| cancelled | pending |

A same-state transition is idempotent and leaves fields unchanged. Dependencies
MUST exist, be unique, and form an acyclic graph. In-progress/done tasks MUST have
only done dependencies. A blocked task needs a reason. Entering done needs a
nonempty result and fresh passing evidence. A done task cannot be reopened while
an in-progress or done task depends on it. Returning to pending clears worker,
result and evidence. Returning to other states clears the resolved blocker.

The reference CLI's claim operation atomically checks readiness and ownership,
sets in_progress and selects the task. Reclaim by the same worker is idempotent;
a different worker requires an explicit reset through blocked/pending. Locks are
local to a checkout. Separate Git worktrees require coordinator ownership; copied
state does not globally synchronize claims.

## Verification and evidence

A command is `{ "argv": ["program", "arg", ...], "timeout_seconds": 600 }`.
Commands run sequentially from the workspace root with null stdin. There is no
implicit shell. Programs inherit the host environment; the reference CLI sets
NO_COLOR and CARGO_TERM_COLOR to suppress color. A shell is possible only when
explicitly included in argv. `verify --allow-exec` is authorization to run the
saved commands. `run -- argv...` directly authorizes the supplied command.

Commands must remain in the foreground until their work completes; detached
background work is outside the verification contract. Raw stdout/stderr are
separate complete files. Cross-stream interleaving is not
preserved. Each versioned RunSummary records literal argv, exit status, timeout,
duration, relative raw artifact paths, bounded unique diagnostics and a short
tail. Nonexistent programs have null exit status and a launch diagnostic. Nonzero
exit, timeout or source mutation makes verification fail. All declared commands
run even if an earlier command fails. An interrupted CLI may leave partial raw
artifacts; no passing evidence is inferred from those files.

Evidence stores source and contract hashes plus the latest run receipts. It is an
assertion from a trusted local client, not signed proof. Readers MUST distinguish
unverified, passed, failed, and stale. Missing raw artifacts do not erase the
receipt but MUST be reported when inspecting evidence. Old done tasks remain
historical results; source edits do not automatically reopen all completed work.

Reference fingerprint algorithm (`aiw` v0.1): SHA-256 over compact JSON of a sorted
map of relative file paths to content hashes. Regular file hashes cover bytes and,
on Unix, the executable permission bits as a little-endian u32. Symbolic links hash
`symlink:` plus the link target, without reading targets. Submodule directories
hash their HEAD string; dirty submodule internals are not covered. Git supplies
tracked and nonignored untracked paths; missing tracked paths disappear from the
map. Non-Git mode uses an ignore-aware filesystem walk. Excluded: `.ai/state.json`,
`.ai/runtime/`, `.ai/derived/`, `.git`, target, node_modules, .venv and __pycache__.
Other policy/decision files are covered when included in discovery.

The contract hash covers compact JSON of the ordered tuple: task title, plan ID,
plan object, dependency IDs, scope, acceptance, constraints, verify commands,
project invariants. Worker, status, result and checkpoint are excluded. Other
clients MUST treat hashes they cannot reproduce as requiring re-verification;
they MUST NOT translate an old pass into fresh evidence by changing its hashes.
Fingerprint details are reference implementation behavior, not a frozen cross-OS
build protocol. A receipt may become stale when moving between operating systems.

Freshness does not cover ignored configuration, environment variables, installed
tools, remote services, or external dependencies. Builds are not hermetic. A file
changed and restored during a command may not be detected. Hostile programs can
forge state; AIW is not a security boundary.

## Mutation, recovery, and versions

Clients MUST validate before replacing canonical state. The reference client uses
an OS exclusive file lock at `.ai/runtime/write.lock` and an fsynced same-directory
temporary file followed by atomic replacement. Locks release when the process
dies; the lock file itself may remain. Readers observe the old or new state.
Symlink components in AIW-managed paths are refused. Concurrent noncooperating
editors and hostile filesystem races are outside the trust model. Back up through
Git; no automatic commit, reset or merge occurs.

A newer or older unsupported schema MUST fail closed without changing canonical
state. v1 is the first format; no legacy migration exists. A future migration must
validate source version, write a backup, explicitly transform and validate state,
then atomically replace it under lock. Never relabel an unknown version as v1.

`init` preserves existing state/policy, fills missing scaffold files, and refreshes
derived discovery. `load` reads state and current Git/source facts; it never runs
acceptance commands. Default output ≤8,192 UTF-8 bytes; configurable 2,048–32,768.
It selects explicit task, active task, in-progress task, or dependency-ready pending
task in the active plan, using stable ID order. Completed history is omitted unless
explicitly requested. Truncation MUST be visible with a drill-down instruction.
State parsing cost can grow with history even though output does not.

Skills, vendor instruction files, and lifecycle hooks are noncanonical adapters.
They MAY inject `load` output at session start. A strict stop hook MAY request one
additional agent turn while the active task is pending or in progress, but MUST
allow a repeated stop attempt and MUST allow persisted blocked or terminal state.
This guard enforces state persistence, not semantic correctness. Only the task
state machine and fresh verification evidence permit a transition to done.

## Derived and runtime formats

Index v1 contains provenance `aiw-lexical-v1` and a sorted map of file hash, bytes,
line count, and searchable flag. Every refresh rehashes inputs; unchanged extraction
is reused. Text retrieval accepts UTF-8 files ≤1 MiB, skips binaries and symlinks,
and returns literal case-insensitive matches with 1-based lines. It is lexical,
not semantic. Corrupt/incompatible indexes are rebuilt. Search refreshes before
reading source; no cached source prose is returned as fact.

Inspection v1 reports language extensions, manifests, CI, likely test files,
documentation, agent configurations and suggested Rust verification argv. These
are deterministic heuristics, not execution or semantic test discovery.

Optional `--events` appends runtime JSONL with schema_version, operation name,
success, duration_ms and optional AIW_AGENT/AIW_PROVIDER/AIW_MODEL values. No token
or cost estimates are invented. There is no telemetry upload. Runtime formats may
be extended independently; a future incompatible structure must change its version
or provenance. Raw logs can contain secrets and consume disk; dispose of runtime
only when no operations are running, then re-run needed verification.
